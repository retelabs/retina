## What `crates/orchestrator` does

The three services of dossier step 6 (`ClickHouse`, `kernel`, `query-api`),
deployed in dependency order, behind an HTTP API (see below).

```rust
pub enum ImageSource { Registry, Local, Build { context, dockerfile } }

pub struct PortSpec { pub container_port: u16, pub host_port: u16 }

pub struct ManagedService {
    pub name: String,
    pub image: String,
    pub image_source: ImageSource,
    pub env: Vec<String>,
    pub healthcheck: Option<HealthCheckSpec>,
    pub ports: Vec<PortSpec>,
    pub depends_on: Vec<String>,
}

pub async fn ensure_running(docker: &Docker, network: &str, service: &ManagedService) -> Result<(), OrchestratorError>;
pub async fn ensure_network(docker: &Docker, name: &str) -> Result<(), OrchestratorError>;
pub async fn deploy_all(docker: &Docker, network: &str, services: &[ManagedService]) -> Result<(), OrchestratorError>;
pub async fn teardown_all(docker: &Docker, services: &[ManagedService]) -> Result<(), OrchestratorError>;
pub async fn status(docker: &Docker, name: &str) -> Result<ServiceStatus, OrchestratorError>;
pub async fn wait_healthy(docker: &Docker, name: &str, timeout: Duration) -> Result<ServiceStatus, OrchestratorError>;
pub async fn teardown(docker: &Docker, name: &str) -> Result<(), OrchestratorError>;
```

`ensure_running`/`ensure_network`/`teardown` are **idempotent**, the central
property of a real control plane: a reconciliation loop must be able to call
"converge to this state" again without caring about the starting state, including
under concurrent calls (see the race finding below). `deploy_all` sorts
`services` by dependency (a topological sort, Kahn's algorithm, deterministic:
ties are broken by input order, not by `HashMap` iteration), then for each one in
that order runs `ensure_running` + `wait_healthy` before moving on. When a
dependent service starts, everything it depends on is already healthy. That is
exactly what `depends_on: condition: service_healthy` gives under
`docker compose`, rebuilt from the API.

**A shared network, not the default `bridge` network**: containers on Docker's
default `bridge` network do *not* resolve each other by name (only by IP); only a
user-defined network gives name resolution. `deploy_all` creates such a network
(`ensure_network`) and attaches each container to it (`HostConfig.network_mode`)
so that `kernel`/`query-api` reach
`CLICKHOUSE_URL=http://<clickhouse container name>:8123`. Verified by pushing a
real fraudos replay over gRPC through the stack deployed by the orchestrator,
then reading the metrics back through `query-api`, not only by reading
`docker inspect`.

## Real findings, not guessable from a summary of the docs

1. **`create_image` (image pull) returns a `Stream`, not a `Future`**:
   `docker.create_image(options, None, None)` pulls nothing until the stream is
   consumed (`while let Some(event) = pull.next().await`). Calling the function
   without doing so compiles and silently does nothing.
2. **`ContainerCreateBody`/`CreateContainerOptions`, not `Config<String>`**:
   bollard's type names changed between versions (generated from Docker's OpenAPI
   schema rather than hand-written). Coding from memory of an older version of the
   crate would have produced code that does not compile.
3. **Telling "never created" from "exists but stopped"** takes
   `list_containers(all: true)` filtered by name (`^/<name>$`), not
   `inspect_container` alone: `inspect_container` on a missing name returns an HTTP
   error that must be interpreted, whereas `list_containers` directly gives an
   empty list or not, simpler to handle without depending on the exact error code.
4. **`ensure_network` had a real race** (found by the crate's own test suite, not
   built on purpose): check-then-create (`list_networks`, then `create_network`)
   leaves a window where two concurrent callers both see "does not exist" and both
   try to create; the loser gets a `409`. Fixed by treating `409 (already exists)`
   as success, the same logic as the `304 (already started)` already handled for
   `start_container`. Reproducible at will: `cargo test -p orchestrator --
   --ignored` runs two tests that call `ensure_network` on the same name in
   parallel by default.

## Container health (`ServiceStatus`)

Reflects `ContainerState.health.status` (`HealthStatusEnum`: `NONE`, `STARTING`,
`HEALTHY`, `UNHEALTHY`, plus `EMPTY` for an empty string from the API) as Docker
itself computes it from the `Healthcheck` declared when the container is created:
the same mechanism `docker/docker-compose.stack.yml` already uses for
`clickhouse` (`wget --spider -q http://localhost:8123/ping`, the `["CMD", ...]`
form, not `CMD-SHELL`, reproduced identically in `ManagedService`).
`wait_healthy` is a miniature reconciliation loop: observe the state, compare it
with the desired state, wait, repeat. The same principle as a real
Kubernetes/Nomad controller, reduced to its simplest form.

## HTTP API (`crates/orchestrator/src/api.rs`)

`main.rs` is a real service (`axum::serve`), with the same layering as
`crates/query-api` (routes and DTOs separate from the client doing the real
work), for consistency across the workspace.

| Route | Effect |
|---|---|
| `GET /status` | Status of the three services (`ServiceStatus`, serialised as is: a C-like enum becomes a JSON string by default with `serde`). |
| `POST /deploy` | `deploy_all`, then returns the status. **Idempotent**: a caller can call it again after a timeout without checking the state first. |
| `POST /teardown` | `teardown_all`, then returns the status. Idempotent too. |

Error mapping (`ApiError: From<OrchestratorError> + IntoResponse`):
`UnknownDependency`/`DependencyCycle` → 400 (the request itself cannot work),
`MissingLocalImage` → 422 (understood but not executable as is: a prior
`docker build` is missing), `HealthTimeout` → 504, `Docker(_)` → 500. Telling
these cases apart rather than returning 500 for everything saves the caller from
guessing what to check.

**Authenticated (2026-08-16)**: the same mechanism as `crates/kernel`/
`crates/query-api` (`docs/interfaces/kernel-auth.md`): `ORCHESTRATOR_API_KEY`,
fail-closed at startup, the header `authorization: Bearer <token>`, with
`src/auth.rs` duplicated from `query-api`'s rather than factored out.
`ORCHESTRATOR_BIND` defaults to `127.0.0.1` (not `0.0.0.0` like
kernel/query-api): authentication adds to that caution, it does not replace it.
This surface can stop containers, more sensitive than kernel or query-api, not
less.

Verified at two levels: `tower::ServiceExt::oneshot` against the real `Router`
(`crates/orchestrator/tests/api_integration.rs`, `--ignored`), a full cycle
`/status` → `/deploy` → `/deploy` again (idempotence) → `/teardown` against the
real three-service stack, not a toy topology; and manually, with the server
really started (`cargo run -p orchestrator`), `curl` against the three routes,
then a real gRPC replay (`fraudos-replay`) and a real `query-api` request
confirming that the containers deployed through the HTTP API really work, not
only `status: "Healthy"`.

## Image builds through the API (`crates/orchestrator/src/image_build.rs`)

`kernel`/`query-api` use `ImageSource::Build { context, dockerfile }`: no external
`docker build` is needed before `deploy_all`. `ensure_image` builds a tar of the
context in memory, sends it to `POST /build` (`bollard::Docker::build_image`), and
consumes the progress stream to the end (or an error).

- **The same context as `docker-compose.stack.yml`**: the repository root
  (`crates/orchestrator` → `../..`, resolved through `CARGO_MANIFEST_DIR`),
  because `kernel.Dockerfile`/`query-api.Dockerfile` do `COPY . .` of the whole
  Cargo workspace, not only their own crate.
- **`.dockerignore` honoured, but deliberately reduced**: matching by path
  component at any depth (`target/`, `.fastembed_cache/`, `.git/`, `.github/`,
  `*.md`), with no anchoring through a leading `/` and no `!` negation. This
  repository's real `.dockerignore` needs neither; documented as an accepted
  reduction, not a partial reimplementation pretending to be complete.
- **Built on every deployment**, not only when the image is missing: the same
  semantics as `docker build`/`docker compose build`. Docker's layer cache makes an
  unchanged context quick to rebuild; deciding when to rebuild is not ours.
  **Known limit**: `ensure_image` (hence `Build`) only runs when the container
  does not exist yet. A container already started from an older image is not
  recreated automatically after a rebuild; it has to be destroyed first.
- **`ImageSource::Local` remains available** for a service whose image this
  control plane should neither pull nor build. Not used by the Retina topology
  today, but a valid choice of the API.

A real finding: `BuildInfo` (each event of the `/build` stream) has no flat
`error` field like `CreateImageInfo`, only `error_detail: Option<ErrorDetail>`.
Guessed wrong once by writing the code by analogy with `create_image`, corrected
by rereading the real struct in `bollard-stubs`.

Verified against a real Docker daemon, not only compiled: a dedicated test really
builds `docker/kernel.Dockerfile` through the API (`cargo build --release -p
kernel` actually runs in the builder container, ~64 s cold) and then confirms the
image produced has the right `ENTRYPOINT`
(`crates/orchestrator/tests/build_integration.rs`, `--ignored`). And really end to
end: `POST /deploy` now builds `kernel`/`query-api` itself before starting them
(`crates/orchestrator/tests/api_integration.rs`), followed by a real gRPC replay
(`fraudos-replay`) and a real `query-api` request confirming that the image built
by our own code really works.

## How it was verified (kernel/query-api update)

Really end to end, not only `docker inspect`: `cargo run -p orchestrator --
--keep-running` deploys the three services, then a real gRPC replay
(`fraudos-replay`) against `localhost:4317` and a real authenticated HTTP request
against `localhost:8080/metrics/summary` confirm that `kernel` really wrote to
ClickHouse (through the container name resolved on the shared network) and that
`query-api` reads the same data back. Plus the automated tests: 4 unit tests for
`topological_order` (correct order, unknown dependency rejected, cycle rejected,
determinism) without Docker, and the `--ignored` integration tests against a real
daemon (idempotence on one service, `deploy_all`/`teardown_all` on a two-service
dependency chain, the HTTP API cycle, the image build), all run by
`scripts/test-integration.sh --with-docker` and in CI since 2026-09-30.
